### py-005

**Check-then-act on shared state lets every thread register the same job**

`critical` · `concurrency` · [`snippets/python/py-005_check_then_act_race.py`](../snippets/python/py-005_check_then_act_race.py) · lines 23, 26

**Mechanism**

The membership test on line 23 and the insertion on line 26 are separate operations with arbitrary work between them. _prepare blocks, and a blocking call releases the GIL, so the interpreter switches threads while callers are sitting between their check and their act. Each of them has already observed an empty _jobs, so each proceeds to insert.

The GIL is what makes this easy to miss. It does make each individual dict operation atomic, so no dict is ever corrupted and nothing raises. What it does not make atomic is the check-act pair, and the function's entire contract, stated in its own docstring, depends on that pair being indivisible. Reasoning that the GIL makes Python free of data races is correct about memory and wrong about invariants.

The width of the window is the duration of _prepare, which means the defect is invisible in a unit test that stubs the network call out and severe in production where the call is slow. Test coverage here is actively misleading.

**Trigger**

Fifty threads calling register('job-1', ...) concurrently while _prepare takes 10 ms. Every thread reaches line 23 before any thread reaches line 26.

- Observed: 'one job id, submitted 50 time(s)'. All fifty callers receive True, _submitted holds fifty entries, and _jobs['job-1'] holds whichever payload happened to be written last.
- Expected: 'one job id, submitted 1 time(s)', with one caller receiving True and forty-nine receiving False.

**Fix**

```python
_lock = threading.Lock()
_CLAIMED = ""

def register(job_id: str, payload: str) -> bool:
    """Register a job idempotently. Returns True if this caller created it."""
    with _lock:
        if job_id in _jobs:
            return False
        _jobs[job_id] = _CLAIMED       # claim the id before releasing the lock
    try:
        prepared = _prepare(payload)   # slow work runs outside the lock
    except Exception:
        with _lock:
            _jobs.pop(job_id, None)    # release the claim so a retry can succeed
        raise
    with _lock:
        _jobs[job_id] = prepared
        _submitted.append(prepared)
    return True
```

Inserting the claim before releasing the lock is the part that actually closes the race: the check and the state change that invalidates it for everyone else now happen without an interleaving point between them. Simply wrapping the existing body in the lock would also be correct, but it would hold the lock across _prepare and serialize registration of unrelated job ids, turning a correctness bug into a throughput one.

The try/except exists because claiming early creates a failure mode the original did not have: if _prepare raises, the id stays claimed and every retry returns False forever. Releasing the claim on failure is not optional once the claim is made early.

This is correct within one process only. Two processes, or two replicas, each have their own lock and their own _jobs, so real idempotency has to be enforced by a uniqueness constraint in whatever storage both of them share.

**Correct as written**

- _jobs and _submitted being module-level mutable state is a design smell, but it is not the defect. The identical race exists if they are instance attributes on a shared object.
- dict.__contains__ and dict.__setitem__ are individually atomic under CPython's GIL, so no caller can ever observe a half-written dict. That is true, and concluding from it that this function is thread-safe is exactly the mistake this entry records.
- list.append on line 27 is atomic and is not a source of lost entries. The list ends up too long, not corrupted.

**References**

- <https://docs.python.org/3/library/threading.html#lock-objects>
- <https://docs.python.org/3/glossary.html#term-global-interpreter-lock>

### py-006

**One malformed record aborts the batch, which is then reported as a success**

`critical` · `error-handling` · [`snippets/python/py-006_swallowed_batch_failure.py`](../snippets/python/py-006_swallowed_batch_failure.py) · lines 22, 25, 26, 27

**Mechanism**

Two independent mistakes compound here.

First, the try on line 22 wraps the whole loop rather than one iteration. The first ValueError unwinds out of the loop entirely, so every record after the malformed one is never attempted. The docstring promises to skip records that fail to parse, which is per-record recovery, and the structure cannot deliver it: the loop has no way to resume.

Second, except Exception on line 25 followed by pass discards the exception without recording it, and line 27 returns ok: True unconditionally. The caller is told the import succeeded. The imported and total counts do differ, which is the only surviving trace, but nothing in the contract requires a caller to compare them and ok: True actively discourages it.

The combined result is silent partial data loss, and it is indistinguishable from a batch where some records were legitimately skipped. Catching Exception rather than ValueError widens the damage further: a bug inside _parse, or a MemoryError, is absorbed the same way as an expected bad row.

**Trigger**

import_batch(['host=localhost', '=orphaned', 'port=8080']): one valid record, then a malformed one, then another valid one.

- Observed: {'ok': True, 'imported': 1, 'total': 3}. The record 'port=8080' is perfectly valid but is never parsed, and no error is surfaced to the caller.
- Expected: Both valid records imported and the malformed one reported, for example {'ok': False, 'imported': 2, 'total': 3, 'errors': ["missing name in '=orphaned'"]}.

**Fix**

```python
def import_batch(raw_records: list[str]) -> dict[str, Any]:
    """Import every record, skipping ones that fail to parse."""
    imported: list[dict[str, str]] = []
    errors: list[str] = []
    for raw in raw_records:
        try:
            imported.append(_parse(raw))
        except ValueError as exc:
            errors.append(str(exc))
    return {
        "ok": not errors,
        "imported": len(imported),
        "total": len(raw_records),
        "errors": errors,
    }
```

Moving the try inside the loop is what actually provides the per-record recovery the docstring already claims. Narrowing to ValueError means a genuine bug in _parse, a KeyboardInterrupt, or a MemoryError propagates instead of being miscounted as a skipped row. Collecting the messages gives the caller something to act on, and deriving ok from whether any errors occurred makes the flag mean something rather than being a constant.

This changes the return shape, so every caller has to be updated. That cost is the reason the original was easy to leave in place, and it should be stated in the review rather than discovered during the merge.

The fix deliberately does not decide policy. Whether a partially failed batch should be committed, rolled back, or retried is the caller's decision; all this guarantees is that the caller now has the information needed to make it.

**Correct as written**

- _parse raising rather than returning None is the right design for a parse function and is not the defect. Everything wrong here is in how the caller handles the exception.
- raw.partition('=') accepts a record with no '=' and produces an empty value rather than raising. That is deliberate: an empty value is legal, a missing name is not, and line 14 checks the case that actually matters.
- Returning a plain dict rather than a typed result object is loose, but the shape is documented and the caller can read it. It is a style question, not the failure.

**References**

- <https://docs.python.org/3/tutorial/errors.html#handling-exceptions>
- <https://docs.python.org/3/library/exceptions.html#exception-hierarchy>

### ts-002

**Async callback given to forEach is never awaited, so the function resolves before any write**

`critical` · `concurrency` · [`snippets/typescript/ts-002_async_callback_in_foreach.ts`](../snippets/typescript/ts-002_async_callback_in_foreach.ts) · lines 17, 20, 21

**Mechanism**

forEach invokes its callback and discards whatever it returns. An async callback returns a promise, so forEach starts each one and moves straight on, finishing once every callback has been started rather than completed. Control reaches line 21 with every save still pending, so written is still 0 and the function resolves to a count that is not just stale but always zero.

TypeScript does not object. forEach's callback is typed as returning void, and Promise<void> is assignable to void by an explicit rule that exists so callbacks may ignore return values. That convenience is what removes the one signal that would have caught this.

The second consequence is more serious than the wrong count. Each discarded promise is the only handle on its save, so a rejection has no handler attached and surfaces as an unhandled rejection rather than as an error the caller can see or catch. A failed write is therefore invisible at the call site, and a caller that treats the resolved promise as meaning 'durably stored' may acknowledge a request or clear a queue on the strength of it.

**Trigger**

flushOrders with three orders and a save that resolves after 10 ms, with the caller acting on the returned count.

- Observed: Resolves to 0 with nothing yet saved. The three writes complete roughly 10 ms later, after the caller has already continued.
- Expected: Resolves to 3, and only after all three writes have completed.

**Fix**

```typescript
export async function flushOrders(
  orders: Order[],
  save: (order: Order) => Promise<void>,
): Promise<number> {
  await Promise.all(orders.map((order) => save(order)));
  return orders.length;
}
```

map keeps the promises instead of discarding them, and Promise.all is what actually waits. Because a rejection now propagates out of flushOrders, a failed write becomes an error the caller can handle rather than an unhandled rejection the process discovers on its own.

Counting with orders.length rather than an incremented variable is deliberate. Under Promise.all either every write succeeded or the function threw, so a separate counter has no state it could report that the return type does not already imply, and it could only ever disagree with reality.

Two things this fix decides rather than fixes. It preserves the original's full concurrency, which is wrong if save hits a rate-limited service; a for...of loop or a bounded pool is the right shape there. And it adopts all-or-nothing semantics, so the first rejection abandons the result even though other writes may have succeeded. Promise.allSettled is the alternative where partial success has to be reported.

**Correct as written**

- written being captured by the closure is not the problem. The closure does update it correctly; the defect is when it is read, not how it is shared.
- forEach is not deprecated and is not wrong for a synchronous callback. The incompatibility is specifically between forEach and a callback that returns a promise.
- Injecting save as a parameter rather than importing it is a testability choice and has no bearing on the defect.

**References**

- <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/forEach>
- <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/all>
- <https://www.typescriptlang.org/docs/handbook/2/functions.html#return-type-void>

### py-001

**Shared mutable default argument accumulates tags across every call**

`high` · `correctness` · [`snippets/python/py-001_mutable_default_accumulator.py`](../snippets/python/py-001_mutable_default_accumulator.py) · line 9

**Mechanism**

Default argument values are evaluated once, when the def statement executes, and the resulting object is stored on the function object itself (visible as collect_tags.__defaults__). Every call that omits tags therefore binds that same list, so the append on line 13 mutates state that outlives the call. The docstring on line 18 promises one fresh accumulator per record, and that promise is never kept.

A second consequence compounds the first. Because every call returns the same object, summarize stores one identical list under every key, so the values of the returned dict are aliases of each other rather than independent lists. A caller who later mutates result['a'] silently changes result['b'] too, which is a defect that outlives the function that caused it.

**Trigger**

summarize([{'source': 'a', 'tag': 'x'}, {'source': 'b', 'tag': 'y'}]): two records with different sources, each carrying a tag, in a single process.

- Observed: {'a': ['x', 'y'], 'b': ['x', 'y']}, and result['a'] is result['b'] evaluates to True.
- Expected: {'a': ['x'], 'b': ['y']}, with the two lists being distinct objects.

**Fix**

```python
def collect_tags(record: dict[str, str], tags: list[str] | None = None) -> list[str]:
    """Append this record's tag to an accumulator and return the accumulator."""
    if tags is None:
        tags = []
    tag = record.get("tag")
    if tag is not None:
        tags.append(tag)
    return tags
```

Using None as the sentinel moves list construction from definition time to call time, which is the only way to get a per-call object while keeping the parameter optional. It deliberately preserves the mutate-and-return behaviour when a caller does pass a list, because that is a legitimate use of an accumulator and other callers may rely on it.

It does not prevent a caller from passing the same list into two separate calls and recreating the aliasing at the call site. If the function should never share state, the stronger change is to drop the parameter entirely and have the caller do its own accumulation, at the cost of a less convenient signature.

**Correct as written**

- Line 12 uses 'is not None' rather than a truthiness check. That is deliberate and correct: an empty-string tag is a real value that should be recorded, and truthiness would silently drop it.
- collect_tags returns the same object it was given rather than a copy. That is normal for an accumulator and is not the defect; the defect is where that object comes from when the argument is omitted.

**References**

- <https://docs.python.org/3/reference/compound_stmts.html#function-definitions>
- <https://docs.python.org/3/faq/programming.html#why-are-default-values-shared-between-objects>

### py-002

**Report traverses the row iterator twice, so the second pass sees nothing**

`high` · `correctness` · [`snippets/python/py-002_generator_consumed_twice.py`](../snippets/python/py-002_generator_consumed_twice.py) · lines 20, 21

**Mechanism**

parse_rows contains a yield, so calling it returns a generator, not a sequence. A generator is an iterator, and an iterator is consumed by a single traversal. Line 20 advances it to exhaustion in order to count the rows; line 21 then begins iterating an iterator that has nothing left, so the comprehension produces an empty list.

Nothing raises, because an iterator's __iter__ returns itself and iterating an exhausted iterator is legal and simply yields no items. The failure mode is the dangerous one: an empty result that is indistinguishable from the legitimate case where no row lacked a value. The annotation on line 18 is honest about the type, but Iterator carries no guarantee of re-iterability and nothing in the language enforces single traversal.

**Trigger**

report(parse_rows(['host=localhost', 'port=', 'debug=true'])), where exactly one of the three rows has an empty value.

- Observed: '3 rows, 0 empty: []'
- Expected: '3 rows, 1 empty: [\'port\']'

**Fix**

```python
def report(rows: Iterable[dict[str, str]]) -> str:
    """Describe how many rows were parsed and which ones had no value."""
    materialized = list(rows)
    empty = [row["name"] for row in materialized if not row["value"]]
    return f"{len(materialized)} rows, {len(empty)} empty: {sorted(empty)}"
```

The function needs two independent passes and an iterator cannot be rewound, so materializing once is the direct fix. Widening the parameter to Iterable reflects that the function now accepts lists and other re-iterables as well, rather than advertising a constraint it no longer has.

This gives up exactly the laziness parse_rows was written for: the whole batch is now held in memory, which is a real regression for the large-file case its docstring cites. If that matters, the alternative is a single pass that accumulates the count and the empty names together, keeping memory bounded by the number of empty rows instead of the number of rows. That version is harder to read, which is the trade being made.

**Correct as written**

- sum(1 for _ in rows) is an idiomatic way to count an iterator of unknown length and is not wrong on its own. The defect is that a second traversal follows it.
- line.partition('=') on a line containing no '=' returns the whole line as the name and an empty string as the value. That looks like a swallowed parse error but is the documented behaviour, and an empty value is a case the report already handles.

**References**

- <https://docs.python.org/3/glossary.html#term-generator>
- <https://docs.python.org/3/library/stdtypes.html#iterator-types>

### py-003

**Removing from the list being iterated skips the element after each removal**

`high` · `correctness` · [`snippets/python/py-003_mutation_during_iteration.py`](../snippets/python/py-003_mutation_during_iteration.py) · lines 12, 14

**Mechanism**

Iterating a list advances an internal integer index. list.remove shifts every later element down one position, but the loop's index still increments on the next step, so the element that moved into the vacated slot is never visited. Each removal therefore skips exactly one following element, and the skipped element keeps whatever state it had.

Python does not detect this for lists. Dicts and sets raise RuntimeError when they change size during iteration, and that guard trains people to expect the language to catch this class of mistake; lists provide no such check, so the loop completes normally and returns a count that is simply too low.

There is a second, quieter hazard on the same line. list.remove deletes the first element equal to its argument, and dict equality is structural rather than by identity, so two sessions with identical contents would cause the wrong object to be removed.

**Trigger**

A registry whose first three sessions are expired and whose fourth is not: ids 1, 2 and 3 expiring at 10, id 4 expiring at 99, pruned with now=50.

- Observed: 'removed 2, still registered: [2, 4]'. Session 2 is expired but survives the prune.
- Expected: 'removed 3, still registered: [4]'

**Fix**

```python
def prune_expired(sessions: list[dict[str, int]], now: int) -> int:
    """Remove every session whose deadline has passed, returning the count removed."""
    live = [s for s in sessions if s["expires_at"] > now]
    removed = len(sessions) - len(live)
    sessions[:] = live
    return removed
```

Deciding which sessions survive before mutating anything removes the interaction between iteration and removal entirely, rather than patching around it. Counting by length difference also drops the dependence on dict equality that list.remove introduced.

The slice assignment on the last line is load-bearing. sessions[:] = live mutates the caller's list in place, preserving object identity for anyone else holding a reference. Writing sessions = live instead would type-check, pass a test that inspects the return value, and silently stop affecting the caller at all. That is a strictly worse bug than the one being fixed, and it is the most likely way for this fix to be applied wrongly.

It does not make the function safe under concurrent mutation; another thread appending during the comprehension is still a race.

**Correct as written**

- The comparison uses <= rather than <, so a session expiring exactly at now is treated as expired. That is the conventional reading of a deadline and is applied consistently.
- Mutating the caller's list rather than returning a new one is part of this function's contract, signalled by the int return type, and is not the defect.

**References**

- <https://docs.python.org/3/tutorial/controlflow.html#for-statements>
- <https://docs.python.org/3/library/stdtypes.html#mutable-sequence-types>

### py-004

**Naive UTC timestamp is compared against naive local time, expiring tokens early**

`high` · `correctness` · [`snippets/python/py-004_naive_and_local_datetime_mix.py`](../snippets/python/py-004_naive_and_local_datetime_mix.py) · lines 17, 23

**Mechanism**

Both operands on line 23 are naive datetimes, so Python compares them without complaint. Mixing a naive and an aware datetime raises TypeError, which is the language's one guard in this area; two naive values are instead assumed to share a timezone.

Here they do not. Line 17 produces a correct UTC instant and then strips the tzinfo, leaving a naive value whose wall-clock reading is UTC. datetime.now() on line 23 returns a naive value whose reading is the host's local time. The comparison is therefore off by the host's UTC offset, always in the direction that makes tokens appear older than they are for hosts east of UTC.

The replace(tzinfo=None) call is the precise step that destroys the information Python would otherwise have used to reject the comparison. Note also that on a host configured for UTC the two readings coincide and the file behaves correctly, which is why this class of defect routinely survives a CI suite that runs in a UTC container and only appears on a developer's machine or in one region.

**Trigger**

Run on a host with a non-zero UTC offset (this entry was annotated on a UTC+09:00 host), issue a token with a one-hour TTL, and check it immediately.

- Observed: 'expired? True' immediately after issue. expires_at reads 2026-09-08 22:41 while datetime.now() reads 2026-09-09 06:41, a nine-hour gap that is purely the UTC offset.
- Expected: 'expired? False' for the first hour after the token is issued.

**Fix**

```python
def is_expired(token: dict[str, datetime]) -> bool:
    """Return True once the token's expiry has passed."""
    now_utc = datetime.now(timezone.utc).replace(tzinfo=None)
    return token["expires_at"] <= now_utc
```

This makes both operands naive-UTC, matching the convention line 17 already established and the shape the storage column requires. It is the smallest change that restores correctness and does not touch the storage layer.

It is a patch rather than a cure. The codebase still passes naive datetimes around as if they were UTC, a convention no type checker can verify and the next contributor cannot see from a signature. The durable fix is to keep values aware end to end and convert only at the storage boundary, which has the additional benefit of turning this silent skew into a loud TypeError the first time someone gets it wrong.

**Correct as written**

- Storing a naive timestamp is a constraint imposed by the storage column and is documented in the docstring on lines 14-15. It is what the code is working within, not the defect.
- The comparison uses <= so a token is expired at exactly its expiry instant. That is the intended reading and contributes nothing to the error.
- issue_token itself is correct: datetime.now(timezone.utc) is the right way to get the current instant, and the arithmetic against a timedelta is sound.

**References**

- <https://docs.python.org/3/library/datetime.html#aware-and-naive-objects>
- <https://docs.python.org/3/library/datetime.html#datetime.datetime.now>

### ts-001

**Default sort compares numbers as strings, so the top scores are wrong**

`high` · `api-contract` · [`snippets/typescript/ts-001_default_sort_is_lexicographic.ts`](../snippets/typescript/ts-001_default_sort_is_lexicographic.ts) · line 9

**Mechanism**

Array.prototype.sort called with no comparator converts every element to a string and orders by UTF-16 code unit. For numbers that means '10' sorts before '9', so the result is lexicographic rather than numeric. The zero-argument call is part of the documented signature and the array is typed number[], so TypeScript reports nothing.

A second defect shares the line. Both sort and reverse mutate the receiver and return it, so the caller's array is left permanently reordered by a function whose name and return type both suggest it only reads its input. That side effect is invisible at the call site and outlives the call.

**Trigger**

topScores([9, 10, 100, 25, 3], 3), with the caller keeping a reference to the array it passed.

- Observed: Returns [9, 3, 25], and the caller's array is left reordered as [9, 3, 25, 100, 10].
- Expected: Returns [100, 25, 10], with the caller's array unchanged.

**Fix**

```typescript
export function topScores(scores: number[], limit: number): number[] {
  return [...scores].sort((a, b) => b - a).slice(0, limit);
}
```

The comparator makes the ordering numeric, and sorting descending directly removes the reverse call rather than correcting its input.

Copying with the spread before sorting is the part most likely to be dropped when applying this fix. sort mutates in place, so without the copy the function would still reorder the caller's array even once the ordering is correct, which leaves the harder half of the defect in place while appearing to fix it.

The comparator returns b - a rather than a boolean because that is what the interface requires: a negative, zero, or positive number. Returning a boolean also typechecks and produces an implementation-defined order, which is a common follow-on mistake. This does not handle NaN, which compares false in every direction and will settle in an arbitrary position.

**Correct as written**

- slice(0, limit) with a limit larger than the array returns the whole array rather than throwing, so no bounds check is missing.
- Returning number[] rather than a readonly array is loose, but the mutation happens to the input and not through the returned value.

**References**

- <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/sort>
- <https://tc39.es/ecma262/#sec-array.prototype.sort>

### ts-003

**Type assertion on JSON.parse promises a shape nothing verifies at runtime**

`high` · `type-safety` · [`snippets/typescript/ts-003_unchecked_type_assertion.ts`](../snippets/typescript/ts-003_unchecked_type_assertion.ts) · line 14

**Mechanism**

An as assertion is a claim made to the compiler, not a conversion. It emits no code, so JSON.parse returns whatever the body contained and every function downstream proceeds on a guarantee that was never checked. JSON.parse is declared to return any, and any is assignable to anything, which is precisely why the assertion draws no complaint.

The failure is quiet rather than loud. A body that omits celsius leaves it undefined, and undefined * 1.8 + 32 evaluates to NaN instead of throwing, so a meaningless value propagates into whatever consumes the reading. NaN then compares false against every threshold, so an alerting rule downstream does not fire and the absence of an alert is indistinguishable from a healthy sensor.

Nothing downstream can recover from this. Inside toFahrenheit, reading.celsius has type number, and no amount of strictness there can restore the information discarded on line 14. The assertion sits exactly at the trust boundary, which is both why it is tempting and why it is the only place a check can be added.

**Trigger**

parseReading('{"sensorId":"probe-1"}'): well-formed JSON that omits celsius, which any buggy or hostile client can send.

- Observed: toFahrenheit returns NaN, and no error is raised at any point.
- Expected: The body is rejected at the boundary with an error naming the field that is missing or of the wrong type.

**Fix**

```typescript
export function parseReading(body: string): Reading {
  const parsed: unknown = JSON.parse(body);
  if (typeof parsed !== "object" || parsed === null) {
    throw new TypeError(`malformed reading: ${body}`);
  }
  const { sensorId, celsius } = parsed as Record<string, unknown>;
  if (typeof sensorId !== "string" || typeof celsius !== "number" || Number.isNaN(celsius)) {
    throw new TypeError(`malformed reading: ${body}`);
  }
  return { sensorId, celsius };
}
```

Annotating the parse result as unknown rather than letting it stay any is the change that does the work. unknown forces every subsequent access through a narrowing check, so the compiler starts helping instead of standing aside.

Returning a fresh object built from the narrowed locals means the result needs no assertion at all. The only as that remains is the widening to Record<string, unknown>, which is sound because the preceding check already established that the value is a non-null object. The explicit NaN check is there because JSON can carry a number that is unusable, and typeof alone would accept it.

This validates one shape by hand and does not scale. Past two or three boundary types the right move is a schema validator that derives the TypeScript type from the schema, so the type and the runtime check cannot drift apart. Note also that the fix converts a silent NaN into a thrown error. That is a deliberate escalation: the caller now has to decide what a malformed body means, and that decision belongs at the boundary rather than three functions downstream.

**Correct as written**

- toFahrenheit is correct. Its arithmetic is right and its parameter type is honest; it is simply handed a value that lied about its type.
- Declaring Reading as an interface rather than a class is not the problem. A class would be asserted in exactly the same way, and would additionally lose its prototype and methods through JSON.parse.
- JSON.parse throwing on syntactically invalid input is already handled by the caller in the real system. The gap is valid JSON of the wrong shape, which JSON.parse accepts without complaint.

### ts-004

**Logical OR default discards a caller's explicit zero and empty string**

`high` · `correctness` · [`snippets/typescript/ts-004_falsy_default_clobbers_zero.ts`](../snippets/typescript/ts-004_falsy_default_clobbers_zero.ts) · lines 22, 23

**Mechanism**

The || operator yields its right operand whenever the left is falsy, and falsy includes 0, the empty string, NaN, null and undefined. What this code means to detect is absence, and absence for an optional property is specifically undefined. Every caller that passes 0 or '' is stating a value, and the expression throws it away.

The types encourage the mistake. maxRetries?: number narrows to number | undefined, and || accepts that operand without comment, so nothing signals that the guard is wider than the type it is guarding.

The consequence is inverted from the caller's intent, which is what makes it worth flagging rather than merely noting. maxRetries: 0 means do not retry, and this silently turns it into three retries. The failure mode is doing more work after being told to do less, against a dependency the caller was probably trying to protect.

**Trigger**

resolveOptions({ maxRetries: 0, label: '' }): a caller explicitly disabling retries and clearing the label.

- Observed: { maxRetries: 3, label: 'job' }
- Expected: { maxRetries: 0, label: '' }

**Fix**

```typescript
export function resolveOptions(options: RetryOptions): ResolvedOptions {
  return {
    maxRetries: options.maxRetries ?? DEFAULTS.maxRetries,
    label: options.label ?? DEFAULTS.label,
  };
}
```

?? falls back only on null and undefined, which is exactly the set that means 'not supplied' for an optional property. The guard now matches the type it is guarding.

The substitution is mechanical here but must not be applied mechanically across a codebase. || is the correct operator wherever an empty string or a zero genuinely should be treated as absent, and a blanket find-and-replace would introduce the mirror-image bug in those places.

This does not validate the value. A caller passing a negative maxRetries still gets it through, and whether that should be rejected is a separate question from where the default comes from. Keeping the two concerns separate is intentional; folding validation in here would hide it from callers who supply their own value.

**Correct as written**

- DEFAULTS being a module-level const is safe. It is never mutated and sharing one instance across calls has no effect on the defect.
- Marking the properties optional with ? rather than typing them as number | undefined explicitly is the conventional way to express an option and is not the problem.
- Building a new object rather than mutating options is correct and is what keeps the caller's argument intact.

**References**

- <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Nullish_coalescing>
- <https://developer.mozilla.org/en-US/docs/Glossary/Falsy>

### ts-005

**Spread copy is shallow, so disabling notifications mutates the original**

`high` · `correctness` · [`snippets/typescript/ts-005_shallow_copy_leaks_mutation.ts`](../snippets/typescript/ts-005_shallow_copy_leaks_mutation.ts) · lines 17, 18, 19

**Mechanism**

Object spread copies own enumerable properties by value. The value of notifications is a reference, so the copy holds the very same nested object the original does. Assigning through copy.notifications writes into the original, and the docstring's promise that settings is left untouched is broken on every call.

TypeScript cannot see this. copy and settings have identical types and both permit the assignment, because the type system models shape rather than aliasing. Declaring the nested properties readonly would have made the assignment an error; the interface as written does not.

What makes it survive review is that the mutation is invisible at the call site. The caller receives a correct-looking result and gets no indication that the argument it passed has also changed. The damage surfaces somewhere else entirely, usually as state that is stale in a way that appears impossible from reading the code that observes it.

**Trigger**

withNotificationsOff({ theme: 'dark', notifications: { email: true, push: true } }) where the caller retains a reference to the object it passed in.

- Observed: After the call the original reads { theme: 'dark', notifications: { email: false, push: false } }, and copy.notifications === original.notifications is true.
- Expected: The original is unchanged, and the returned value owns a separate notifications object.

**Fix**

```typescript
export function withNotificationsOff(settings: Settings): Settings {
  return {
    ...settings,
    notifications: { ...settings.notifications, email: false, push: false },
  };
}
```

Spreading the nested object gives it its own identity. Building the whole result as a single expression matters at least as much as the extra spread: there is no longer a moment where a copy exists and is then written to, so the pattern that caused the defect is gone rather than corrected.

This is correct for exactly one level of extra nesting. If Settings grows a deeper structure the same defect returns, silently and with no compiler assistance. The durable defences are to mark the nested types readonly, so the assignment becomes an error rather than a convention, or to hold the state in a structure that is immutable by construction.

structuredClone would also produce a correct result, but it deep-copies everything for a two-field object and would mask rather than express which part of the structure actually needed its own identity.

**Correct as written**

- Returning the same Settings type rather than a distinct branded type is fine; the contract is to return a value of the same shape.
- Setting email and push explicitly rather than mapping over the object's keys is more verbose but is correct, and stays correct if a non-boolean field is added later.
- const on line 17 prevents rebinding copy, not mutation through it. That is standard and is not a misuse.

**References**

- <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Spread_syntax>
- <https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties>

### ts-006

**map passes the element index to parseInt as a radix, so every port after the first is NaN**

`high` · `api-contract` · [`snippets/typescript/ts-006_map_passes_index_as_radix.ts`](../snippets/typescript/ts-006_map_passes_index_as_radix.ts) · line 9

**Mechanism**

map calls its callback with three arguments: the value, the index, and the array. parseInt accepts two: the string and a radix. Passing parseInt directly means each element is parsed in a base taken from its own position.

The specific results explain why this is hard to spot. Index 0 is falsy and parseInt treats a radix of 0 as unspecified, so the first element parses correctly. Index 1 is not a valid radix and yields NaN. From index 2 on, the string is parsed in that base, so '8080' read as binary stops at its first invalid digit and yields NaN as well.

It typechecks because parseInt's parameter list is shorter than the signature map expects, and a function taking fewer parameters is assignable to one taking more. That rule is deliberate and is what lets anyone write .map((x) => x) without declaring two unused arguments; here it is exactly what removes the error. Combined with the first element always being correct, a short or single-element test input produces entirely plausible output.

**Trigger**

parsePorts('80,443,8080'): three comma-separated ports, the shortest input that exposes all three behaviours.

- Observed: [80, NaN, NaN]
- Expected: [80, 443, 8080]

**Fix**

```typescript
export function parsePorts(raw: string): number[] {
  return raw.split(",").map((value) => Number.parseInt(value, 10));
}
```

The arrow function fixes the arity so only the value reaches parseInt, and stating the radix explicitly removes the remaining reliance on parseInt inferring a base from the string's prefix. Number.parseInt is the same function as the global; it is used here only because the namespace makes the intent legible at a glance.

This still does not validate. parseInt('80abc', 10) returns 80 and parseInt('', 10) returns NaN, so a caller that needs malformed input rejected has to check the result, and for something as constrained as a port a range check belongs here too. If any non-numeric input should be an error rather than a NaN, Number(value) is the stricter primitive, since it rejects the trailing garbage parseInt tolerates.

**Correct as written**

- split(',') on a string containing no comma returns a single-element array rather than throwing. That is documented behaviour and is handled correctly.
- Returning number[] containing NaN is type-correct, since NaN is a number. The type system is not wrong here, merely not expressive enough to help.
- Using the global parseInt rather than Number.parseInt has no behavioural difference; they are the same function.

**References**

- <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/parseInt>
- <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/map>
